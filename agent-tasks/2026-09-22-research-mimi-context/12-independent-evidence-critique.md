# Independent evidence critique — Mimi context research (2026-09-22)

Status: **READ-ONLY AD-REVIEW / EVIDENCE LEDGER**

Reviewer: T3 independent evidence critic. Scope was limited to the dated research
folder, the repository QA/UI/harness contracts, and primary public documentation
where a technical claim needed checking. No runtime, provider, API key, browser,
paid eval, or implementation test was used. This file does not approve a design,
route, model, budget, or live run.

## Verdict in one paragraph

The batch is useful as a requirements map and source of competing hypotheses, and
it correctly preserves the Owner's draft/preview distinction, no-unconfirmed-write
boundary, bounded-read idea, context provenance, visible compaction, and the need to
separate deterministic safety from semantic quality. It is **not yet evidence-ready
for T1 synthesis as a factual design**. Several observations are presented as
`FACT` without a measurement or exact source; multiple model names and provider
capabilities are ambiguous/unverified; B08 contains a direct conflict with the
repo UI contract; and B09 proposes a large, costly eval before the Owner has chosen
an architecture, model/route, or budget. T1 should retain the useful hypotheses,
downgrade unsupported claims to `OPEN`/`INFERENCE`, and narrow B09 to an approved
pilot only after the Owner workshop.

## Specific answers to the requested review axes

### Fact / inference / proposal discipline

- **Good and retain:** B03's separation of draft and frozen preview; no-auto-confirm; B06's trust/taint model; B05/B06's insistence on manifests, provenance, deterministic gates and fail-closed writes. These align with the Owner decisions and existing P0/QA contracts, but the final synthesis must still cite the exact contract lines.
- **Needs downgrade:** B03's network/RAM/latency figures, schema error rate, provider-stop behavior, and all numeric loop caps; B08's mobile/tokenizer/cache facts; B09's hard-coded experiment sizes, judge threshold and cost options.
- **Must remain open:** final system prompt, exact context architecture, model/provider/effort, compaction trigger and UX, direct-preview thresholds, second-model policy, eval budget/repetitions/judge, and whether any web/search tool is enabled. None are Owner-approved by `00-owner-decisions.md`.

### Missing compaction and context controls

The research does mention compaction and a divider, but it does not yet provide an implementation-safe contract for: token-count method per route, mandatory-block precedence, truncation/compaction decision record, summary source ranges, pending-preview/steering preservation, recovery after interrupted compaction, and receipt fields for estimated versus provider-reported counts. B08's percentages and example window must not fill these gaps. T1 should synthesize this as a contract question before UI implementation.

The Owner also asked for context size, compaction, model and effort controls in dogfood. B08 proposes UI controls, but no evidence shows the current runtime can expose effective model/effort, provider route, cache usage or a complete context manifest. Therefore the UI should initially show only values backed by a route receipt and explicitly show `UNAVAILABLE`/`ESTIMATED`; it must not invent a meter.

### Draft versus preview preference

The reports generally reflect the Owner's preference: ordinary/read-only turns can answer without mutation; clear small “do it now” requests may produce a typed preview; broad, ambiguous, multi-record or explicitly planning requests should produce a conversational draft first. The mistake is turning illustrative thresholds and keywords into policy. T1 should present this as a policy matrix with examples and ask the Owner to approve the boundary before implementation.

### Eval scope and overengineering

B09 is a thoughtful menu, but it is too large to be the first experiment. The first authorized experiment should be a small, synthetic, version-bound pilot that establishes route capability, receipt completeness, language, draft/preview classification, read-only non-mutation, one confirmed mutation, compaction/recovery only if the implementation exists, and cost/token/latency observations. Future long-context, multi-provider, judge calibration and stress lanes should be separate proposals, not acceptance gates for an architecture that has not been selected.

## Recommendations for T1 synthesis

1. Start the Owner workshop with an evidence table, not a final prompt. Separate `CURRENT_P1` facts from `FUTURE_PROPOSAL` behavior.
2. Retain the hybrid idea as a hypothesis: server-mandatory preflight/context plus bounded C0 reads; never allow the model to choose away capability/privacy/confirmation/CAS gates.
3. Define a provider-neutral context envelope and normalized receipt first. Require exact route card, effective model/effort, source manifest, token-count method, output/tool/safety reserves, cache/cost provenance, and completeness/omission state.
4. Treat structured output as a validation aid, not an authorization boundary. Keep deterministic Pydantic/domain/CAS/confirmation gates regardless of provider.
5. Remove “100% compliance” and unsupported numeric/UI claims from synthesis. Use semantic tokens and actual repository capabilities; keep context meter, inspector, model selector and compaction UI behind readiness gates.
6. Design the first eval around the Owner's real questions (ordinary chat/read-only versus mutation; draft versus preview; tool loop; compaction; UI transparency), then choose cases, repetitions and token cap from measured behavior. Do not choose a dollar cap or judge model prematurely.
7. Keep all research recommendations non-authoritative until B10 Owner workshop is complete. No prompt deployment, live call, model adoption, route change or dogfood should be inferred from these reports.
