# T1 synthesis — reuse-first Mimi and microSched

Date: 2026-09-26. Decision status: **advice for Owner review**, not a runtime/model/architecture approval. Evidence base: local checkout `feat/065-mimi-p1c-context-loop` at `1a10eb4`, the independent Luna rounds in this directory, and the primary sources cited there. No API key, paid inference, install, code change, D10 or live dogfood was used in this research.

## The generalized question

The issue is not whether microSched contains custom code. It is whether we are spending maintenance effort on undifferentiated infrastructure while leaving the product's distinct value—safe natural-language work over Task/Calendar/Notes, transparent preview/confirmation, recovery, and humane interaction—unfinished. The correct unit of comparison is **a seam with its invariants**, not library popularity or lines of code alone.

I recommend a **selective reuse gate before further provider expansion**, not a wholesale pause/rewrite of P1C-B. This gives the Owner a real alternative to the bespoke adapter while preserving the route to D10 and dogfood. The strongest counterargument is that adopting a mature runner or SDK now may avoid future maintenance and shorten P1C-B. That is plausible, but the current evidence has no full contract parity, no measured RSS/startup benefit, and no privacy/unknown-outcome proof for a replacement. The nearest viable alternative is a bounded no-key parity spike of the OpenAI SDK transport, with the current adapter as control, and a separate PydanticAI typed-tool/schema prototype. If one wins against the contract, switch that seam only.

## Provider plumbing gate proposed before D10

1. Freeze current wire contract and count every actual upstream dispatch across success, partial stream, invalid terminal, 429/5xx, connect failure, read failure, timeout and cancel. No key; use synthetic `httpx.MockTransport`/test server. `max_retries=0` must be explicit where an SDK is tried. Compare lock/dependency and process footprint, not just request syntax.
2. Resolve the `store:false` claim separately: an outgoing Chat field and OpenRouter Responses schema do **not** prove Chat retention semantics. Provider ZDR/data-collection routing is a different layer. Exact buyer/route behavior needs authoritative confirmation; do not send private context to an unverified route.
3. Fix any demonstrated recovery or privacy defect narrowly; rerun deterministic contract QA. Preserve current adapter if the SDK merely hides complexity or fails a contract. Only a proven seam swap justifies amending P1C-B or D10 implementation.

This is a **small gate**, not authorization for a rewrite. If an SDK materially wins, Owner should review the transport delta, dependency/rollback and whether D10 route/protocol fixtures change. If it does not, continue with the existing adapter and focus on product experience. D10's live inference, spending, exact route and resource plan still require the Owner's previously requested detailed approval before execution.

## Eval and UX implications

Use the **same real daily STANDARD route policy** in the representative track; pin exact provider/config only in a diagnostic control track so route variance is not hidden. Store buyer-reported usage and cost as reported, with missing values `unknown`, not zero. Do not assume 90–95% prompt cache hits in a cold heterogeneous eval; stratify warm-repeated and cold/changed-prefix cases and track exact model/provider cache receipts. This is a design recommendation, not a measured hit-rate prediction.

For user experience, current source-backed guidance favors immediate truthful feedback, concise answer-first presentation, progressive disclosure and accessible status. The dock should show one current stage, elapsed time and next action; workspace should expose context provenance, source omissions, preview, route and run details. The current `assistant.delta` is terminal-buffered, so UI must not promise live token streaming. External trace stacks add privacy/storage/service cost; the current app ledger plus a small privacy-safe metrics/feedback projection is a better first dogfood loop. W3C status semantics and browser responsiveness should be checked in non-F11, keyboard, reduced-motion and screen-reader states. UX skill heuristics were treated as a search aid, not as current proof; the dated primary references are in report 06.

## Status and proposed next decision

Research folder is local/untracked in this feature worktree; it is **not merged, deployed or accepted as product architecture**. Local code observations and official documentation support the shortlist; actual SDK parity, model quality, route privacy, cost/cache, full QA and live dogfood remain **NOT_RUN / UNVERIFIED** here. Do not confuse this with older offline-green receipts.

Recommended Owner decision: approve the bounded no-key provider parity/recovery gate and truthful-progress/feedback planning as near-term work, while retaining current P1C-B/D10 scope unless measured evidence forces a change. After a focused gate report, T1 can propose any exact code/spec delta and D10 resources for separate approval. Nearest more aggressive alternative: prototype LangGraph plus official SDK now against the same full scenario set; higher discovery upside, but more time, dependency/second-state and regression risk before dogfood.
