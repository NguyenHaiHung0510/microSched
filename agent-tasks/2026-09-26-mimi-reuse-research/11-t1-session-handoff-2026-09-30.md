## Questions the Owner raised and research delivered

1. **Are we reinventing the wheel?** The Owner asked for a generalized audit, not merely a replacement HTTP client. Reports `01`–`09` in this folder cover the current adapter, OpenRouter/OpenAI SDKs, LiteLLM, LangGraph/LangChain, PydanticAI, observability/UX, other microSched reuse opportunities, model selection and Jev. T1 synthesis in `09-t1-synthesis.md` recommends selective reuse and a bounded no-key parity gate, not assuming that bespoke code or a popular framework is automatically best. Nearest more aggressive alternative: full runner parity prototype before dogfood, with higher schedule/dependency/privacy risk.
2. **Why not LangGraph or another famous framework?** Their checkpoint/tool/runtime support is real; they do not own Mimi's privacy, exact Task source versions, Owner approval, frozen preview, idempotent DB write or unknown provider outcome. However this is an engineering hypothesis, **not** proof current loop is optimal. A same-scenario, no-key prototype can overturn it if it measurably reduces recovery/maintenance burden and fits 512 MB RAM/Neon-idle constraints. Do not present framework popularity as a defect or the current implementation as proven best.
3. **Provider plumbing:** current `httpx` adapter encodes one dispatch, route controls, streaming/terminal parsing and unknown-outcome ledger semantics. Official SDK adoption may save maintenance only if the *same* synthetic fixtures prove field fidelity, one upstream POST, no hidden retry, cancellation, usage/provider receipts and privacy behavior. `store:false` being sent is **not** proof of OpenRouter Chat retention policy. The Owner values a standardized service seam and asked for a real challenge to the bespoke adapter. SDK comparison itself is **NOT_RUN**. OpenAI SDK as transport via OpenRouter would not automatically lock the product to OpenAI, but route/protocol compatibility still needs proof.
4. **Jev and alternatives:** Jev is a typed decision model, not Mimi's main conversational agent. The Owner explicitly challenged Jev-only thinking. `07-model-landscape-luna.md` surveys main-model candidates and no-extra-call baselines; `10-decision-model-landscape-update-2026-09-30.md` adds newly observed Kev open-weight family/hosted Kev 4B and Jev Router, which is a different generative-model-router hypothesis. None has a Mimi/Vietnamese, privacy-qualified, cost-per-correct-task win. Consider specialist sidecar only after a held-out comparison against deterministic and existing-model-in-same-turn baselines; keep it optional and vendor-neutral.
5. **GPT-6 Luna:** Official OpenAI Docs state Chat Completions function calling is available with `reasoning_effort=none`; Responses is the route for tools with reasoning. Codex or other harnesses using Luna with reasoning/tool calls are not evidence that Mimi's current OpenRouter Chat-style adapter can do the same. This is a protocol/route gate, not a verdict on Luna quality. Other candidate prices, availability and privacy are volatile; recheck exact provider and buyer route. No Mimi model champion or MIDEX-mini result has been established.
6. **Limits, cache, UX and feedback:** `4 model turns / 6 read-tool calls / 30-minute lease` were baseline engineering parameters, not research-proven universal optima. The Owner wants cap-hit, progress and resume visibility, evidence-based calibration by task/model/route/exception, and no interruption at 60–80% completion just to protect an arbitrary cap. The Owner also asked for user-linked wrong-answer/run feedback with route/stop reason; truthful prompt/cache/cost from buyer receipts, not estimated zero or assumed 90–95% cache hits. Side-chat must stay compact; workspace exposes context/source omissions/run/preview. Immediate local acknowledgment around 400 ms is a UX target, not model completion time. Research is in reports `03`, `06`, `09` and 2026-09-22 B19/B23.
