**📝 2026-07-23 — security review across the *whole* project, not the branch diff.** The default `/security-review` derives its scope from `git diff main...develop`. That convention was sound while `main` meant "reviewed"; since 2026-07-22 `main` is only a lagging release label, so the same command inspected **11 of 47 code files (77% blind)** and the blind spot contained `deps.py`, `sessions.py`, `domain/auth.py` — the security core. **Its failure mode is reporting clean, not reporting an error**: had `main` equalled `develop`, the scope would have been empty. The third was a design decision **nobody had ever made**: `task.*` is encrypted when private but `note` only covers `body_md` — the asymmetry lived **inside one row of `tracking-brief.md` §6**, so both DDLs were faithful and there was no prior decision to respect on either side. **Owner settled it 2026-07-23** (§6, dated note): **`note.title` is encrypted under the flag, matching `task`**; and `note_item`/`task_item` are enforced **app-side, not by the DB** — K11 forbids pushing `is_private` down to child tables and §6's "B-hẹp" posture forbids blanket encryption, so K8/K18 ("PG không nhìn được thì app lo") is the only consistent answer. Two consequences to carry: run 008d **while the tables are empty** (plain DDL migration; after real private data exists it needs backfill), and treat the 008 seam's test as unusually load-bearing, since the child-table invariant has **no DB guard** and 009–012 copy 008's shape. The decisive argument was not the dump threat but a second door: the rule bans embeddings on *encrypted* columns, which silently means plaintext columns are *eligible* — a plaintext private `note.title` could therefore enter pgvector and surface while private mode is locked. **A ban stated one way leaves the other way permitted; say both halves out loud.** **The larger lesson is about which surface to inspect:** `devops-brief.md` §1 states the threat model is *social engineering*, yet a code review touches none of it — reading `docs/` did, and turned up a personal profile assembled from three unrelated files. ## Locked architecture (don't relitigate — see docs for the reasoning)

- **One data store only: PostgreSQL + `pgvector`, hosted on Neon.** No SQLite, no parallel stores. The old app ran SQLite *and* Postgres simultaneously and lost track of which held the truth — that split-brain is the anti-pattern this project exists to avoid.
- **Data model:** see `schema-v1-brief.md`. Core entities: `task`/`task_item`, `note`/`note_item`, `calendar_source`/`calendar_event`, `tracker`/`entry` (unified health + finance logging), `app_setting`, `audit_log`. Principle: **markdown for prose/body fields, structured columns for anything queryable**; timestamps on every entity; store full text, truncate only at display.
